## The shape it wins on

The previous chapter was the negative case; this one is the positive: which settings make this class of model clearly pay. The shape has four conditions, all required.

@fig t23-win

- **Few labels** (two to five): each option gets a generous token budget, and the random baseline sits high enough to leave confidence room to discriminate.
- **High volume** (hundreds of thousands a day): so that 400 ms against 3 seconds, and input-only billing against output-metered, show up on an invoice.
- **Clean semantic boundaries**: questions like whether an input is a prompt injection already have high annotator agreement, the precondition for a learnable boundary.
- **A threshold that separates right from wrong**: the one condition that must be measured, where the first three can be judged by common sense.

## One end-to-end bill

Take prompt-injection detection in front of an LLM app: 500,000 calls a day, an injection rate of three in a thousand, a cost per miss, a cost per false block, an automated share, a volume sent to an LLM for review — producing a monthly net gain compared against sending everything to an LLM and against regex rules. Prompt-injection detection, content safety and model routing all have this shape.

## What this case does and does not prove

Honestly: it is a **cost model** built from public figures and this book's latency measurements, not a real deployment — weaker evidence than the previous fully-measured case, and read it that way. The last chapter proved a task does not work; this one argues a shape might, and the latter still needs your own measurement to confirm.

**Exercise**: tick a candidate setting against the four conditions. If all four hold, go do the module-VI measurement; if any is missing, do not reach for a System One model yet.
