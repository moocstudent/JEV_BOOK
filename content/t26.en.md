## Three locations, not one

'Is the model local, in an external library, or remote?' is confusing because the word 'model' hides three things that live in three different places.

@fig t26-runtime

- **① Your script** (this book's companion demo `laya_check.py`, say) is **local** and contains **no model and no weights**. It is orchestration plus pure-Python statistics: ECE, a temperature grid search, the threshold table. Its entire contact with the model is two lines — `laya.load(...)` and `agent.predict(...)`.
- **② The `laya` pip library** is also **local** but **also holds no weights**. It is nine small `.py` files (~117 KB), the *code* to load and run the model; the real tensor compute is handed to the `torch` and `transformers` it depends on.
- **③ The weights** are the ~400M-parameter network itself, downloaded from Hugging Face (`convaiinnovations/laya`) and **cached locally** to `~/.cache/huggingface` (english 843MB / multilingual 678MB / typed-decisions 846MB).

**The key conclusion**: once the weights are cached, inference runs **entirely on your local CPU**, and `agent.predict` sends not a byte to any remote API. That is the root difference from Jev — Jev is a hosted remote endpoint you POST to; Laya is the open implementation you run yourself. The only remote step is the one-time weight download.

## Loading: what happens before the first forward pass

`laya.load()` runs `Agent.__init__`: if the checkpoint is not local it `snapshot_download`s it from HF (with `allow_patterns` restricted to just this checkpoint's `model.safetensors`, `rl_agent_config.json`, `tokenizer/`, `encoder/`), then `build_model()` reconstructs the network and `load_state_dict(weights, strict=True)` fills in the trained parameters. The device resolves to CPU here (no CUDA). The shipped temperatures are read and **clamped** at this step too — the 0.1006 `choice:11+` bucket is exactly where `TEMP_MIN=0.5` refuses it.

## The library's model: DecisionModel

The library's model is `DecisionModel` (`common.py`):

```
DecisionModel =
    encoder      # bidirectional encoder: ModernBERT-large (en) / mmBERT-base (multi)
  + type_emb     # nn.Embedding(3, d): a learned vector per question type
  + head         # a small two-layer nn.TransformerEncoder
  + scorer       # LayerNorm → Linear(d,d) → GELU → Linear(d,1): any token → one scalar
```

**The defining choice: there is no fixed classification head.** A normal classifier has one neuron per label on a head; Laya does not. Its `scorer` maps *any* token's hidden vector to a single scalar — which is why options can be arbitrary text, and why they compete with the document for the token budget (see LY2).

## Six steps of the forward pass

`agent.predict` = `agent.system_one`, done in **one non-autoregressive forward pass** (`DecisionModel.forward` in `common.py`):

1. **Options become text with markers.** `build_sequence()` serializes state + instructions + each option into one token sequence and records the position of a marker at each option.
2. **One encoder pass.** `h = encoder(input_ids, attention_mask).last_hidden_state` — bidirectional, every token sees every other (fine, since nothing is generated left to right).
3. **Inject the question type.** `h = h + type_emb(qtype)`.
4. **A small head refines** `h`.
5. **Gather at the markers.** `m = gather(h, marker_pos)` pulls the hidden vector at each option's marker, and `logits = scorer(m)` makes **one logit per option**; padding markers are masked to `-1e4`.
6. **Turn into a typed answer** (`agent.py`): `z = logits[:k] / t_scale`, `p = softmax(z)`. choice takes argmax; score takes the ordinal expectation `Σ i·p[i]`; noul takes `p[1]`. `confidence = 1 - H(p)/log(k)` — normalized entropy, **not a probability** (see CA1).

This 'score each option marker and softmax' mechanism explains in one line why it is fast (one pass, no generation loop, no KV cache) and why it collapses on many labels (77 markers all fighting for `head_max_len` room in one sequence).

## The honest seam: inference reproduced, training only approximated

There is **no** RLCD in this inference code — the training method that made the probabilities calibrated. That is baked only into `model.safetensors`. The runtime merely *applies* what training produced (reading the bucketed temperatures from `rl_agent_config.json`, and refusing the bad one). So this open library reproduces Laya's **inference** exactly, but the **training** that calibrated it is only approximated — which is why every 'open Jev' is a re-derivation, not a clone.

**Exercise**: run `pip show -f laya` on your own machine to see how small the library is and that it holds no `.safetensors`; then `du -sh ~/.cache/huggingface/...` to see where the weights are and how big. Confirm with your own eyes that the 'library' and the 'weights' are two different things.

## Appendix · Runtime, switching and re-training

The chapter covered how it runs; this appendix answers the three questions that follow immediately: what the weights look like on disk, whether you can switch models, and whether you can re-train.

### What the HF cache actually is

`~/.cache/huggingface/hub/models--convaiinnovations--laya/` is not a pile of model files — it is a **content-addressed git mirror**:

@fig t26-cache

- `refs/main` — 40 bytes recording the commit SHA that `main` points at.
- `blobs/` — the actual file contents, each named by its hash and **deduplicated** across revisions (10 blobs here, 1.5 GB).
- `snapshots/<SHA>/` — a view of one git revision where every file is a **symlink into blobs**, not a real copy. That is why two revisions, or a resumed download, never cost double the space.

One snapshot **bundles two checkpoints**: the root is English (ModernBERT-large, `model.safetensors` 843 MB), the `multilingual/` subfolder is multilingual (mmBERT-base, 644 MB). Note `typed-decisions/` is **absent** — `allow_patterns` (`agent.py`) fetches only the checkpoint you `load`ed, and I only used English and multilingual, so the third was never downloaded. Each checkpoint = `model.safetensors` + `rl_agent_config.json` + `tokenizer/` + `encoder/config.json`.

### Can you switch models? How?

Yes, at three levels — with one hard boundary.

- **Between the bundled checkpoints**: `laya.load("convaiinnovations/laya", subfolder="multilingual")` (or `"typed-decisions"`), or let the `Router` pick by language (LY1).
- **To any repo or local directory**: `laya.load("some-org/my-ckpt")` or `laya.load("./my_run")`.
- **What you cannot do**: point it at a bare base BERT. The loader `_verify_compatibility` (`agent.py`) requires a **Laya-format decision checkpoint** — the config must have `encoder` + `head_layers`, the safetensors must contain `encoder.` + `type_emb.` + `scorer.` + `act_head.` prefixes, and it loads `strict=True` with per-tensor shape checks. A plain ModernBERT has no decision head, so it is rejected. You also cannot swap the encoder independently of the head — they are one trained unit; the config's `encoder` field only tells the library which architecture to build empty before pouring the trained weights in.

### What a model must have to be loadable

| File | Required | Purpose |
|---|---|---|
| `rl_agent_config.json` | **yes** | at least `encoder` (a transformers id/dir) + `head_layers`; also `max_len` / `head_max_len` / `temperature` / `temperature_by_options` |
| `model.safetensors` | **yes** | state_dict matching `DecisionModel(encoder, head_layers, n_act)` exactly |
| `tokenizer/` | recommended | else it falls back to the encoder's own tokenizer |
| `encoder/config.json` | recommended | lets it rebuild the architecture offline without pulling the base model |

Runtime: Python 3.10–3.13 (not 3.14), `torch≥2.0`, `transformers≥4.48` (needs ModernBERT support), `safetensors`, `huggingface_hub`, `numpy`.

### Can it be fine-tuned again? — Yes, and it is the intended path

Three pieces of evidence, all on disk:

- **The base is meant to be specialised.** The README states the base is near-chance zero-shot on typed-decisions (0.362 vs 0.318 random); the 0.766 comes from fine-tuning on that benchmark's own training split. The English checkpoint's config even records `"fine_tuned_from_checkpoint": true`, `"updates": 7313`, `"hours": 1.96` — it was itself fine-tuned.
- **The library ships the training objective.** `common.py` contains `proper_reward` (a strictly proper scoring rule: log + spherical + ranked-probability), exported publicly alongside `td_lambda_targets`, `ece_score`, `DecisionModel` and `build_model`. The full training loop lives in the fine-tuning notebook the README points to (fit calibration on a held-out slice, clear stale temperatures, push to hub).
- **It is built for cheap fine-tuning.** `DecisionModel.forward` takes a `detach_encoder` flag — set it and only the decision head trains while the encoder stays frozen, the CPU-feasible path on a machine like this one; full fine-tuning of the 400M encoder wants a GPU (the notebook targets 2×T4).

**The re-training recipe**: `build_model(cfg, encoder_dir)` → forward to distributions, compute `proper_reward` against your targets and backprop (the head, optionally the encoder) → fit one temperature per `(qtype × option-count)` bucket on a held-out slice → save `model.safetensors` + `rl_agent_config.json` to a folder → `laya.load("./that_folder")`. This is exactly the fix the book's failure case (CS1/t22) prescribes for the 佳悦 data: stop swapping models — fine-tune the typed-decisions checkpoint on your own rows, because the base is a foundation, not a finished engine.

### The companion demo: agent and fine-tuning (measured)

Everything in this chapter is made runnable in the companion repo `layademo` (Gitee):

- **`app.py` · a FastAPI decision agent** (master branch): wraps Laya + a module taxonomy into a service with a **confidence gate** — `/classify` returns module + confidence + `action` (auto/escalate), `/triage` answers module + urgency + a structural flag in one forward pass, `/batch` reports an auto-rate. It is OP3's two-tier architecture. Measured, it works honestly: a low-confidence requirement misrouted to 财务核算 was correctly `escalate`d by the gate; `/triage` answers three questions in one ~900 ms warm pass. Every response carries a `note` that confidence is normalized entropy (not a probability) and the un-fine-tuned base is a routing hint, not ground truth.
- **`train.py` · frozen-encoder fine-tuning** (train branch): runs the LY4 appendix re-training recipe for real — freeze the encoder, train the decision head with `proper_reward` alone, fit a held-out temperature, save a checkpoint `laya.load` reads back directly. Measured on this CPU with the synthetic sample, 120 rows / 5 epochs: **accuracy 0.733 → 0.767** (loss 0.44→0.34, monotonic), reloaded-from-disk matches. The +3.4 is not the script's fault — the residual errors are the two deliberately-overlapping label pairs (库存管理/仓储作业, 生产计划/生产执行), exactly CS1's lesson: a task problem, not a model problem. Real gains need unfreezing the encoder (GPU) or merging the overlapping labels first.

In one line: **the agent proves the two-tier gate holds in a real service, and the fine-tuning demo proves the 'don't swap models, fine-tune the base' path runs and yields a real delta** — neither is on paper, and every number is measured on this machine.
