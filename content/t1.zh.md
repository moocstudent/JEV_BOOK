## 你要的不是一段话,是一个能拿去 if 的值

你的代码需要一个判断:这张工单归哪个部门、这条评论有没有辱骂、这个请求该走小模型还是大模型。过去三年的标准做法是写一段提示词,让 LLM 输出一段 JSON,再解析出那个字段。这条路能跑,但它的失败模式很特别——不合法的 JSON、合法但字段名漂移的 JSON、同一输入两次不同答案、枚举值被拼错一个字母。

@fig t1-pipes

于是工程上长出了一整套补丁:约束解码保证语法、schema 校验挡住脏数据、重试和修复提示词兜住偶发失败。这些补丁解决的是**格式**,却没有解决更深的问题——你拿回来的那个字符串背后没有概率。你不知道模型有多确定,也就没法按确定程度分流,只能全信或全不信。

## 四类失败,和它们的代价

- **截断 / 非法 JSON**:硬失败,会报错,重试能救,但重试把 P99 拉成 P50 的好几倍。
- **字段漂移 / 枚举拼错**:最危险的一类。JSON 合法、校验通过,但值是错的——没有报错,重试也救不了。

System One 的提法是把这一层直接翻过去:输入程序状态和若干个类型化问题,输出带概率的答案,没有文本生成,也就没有要解析的东西。

## 什么时候不值得换

如果你已经在跑一个 LLM、而且这个判断很低频,那生成再解析的额外成本可以忽略。System One 模型的收益出现在**高频的小决策**上——每天几百万次、每次只要一个枚举和一个概率。

**练习**:找你代码里一处「让 LLM 输出 JSON 再解析」的地方,数一数它有几行是在处理格式失败。那些行就是你为一个不需要的能力付的账。
