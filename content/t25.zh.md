## 一个提法背后的两种问题

你一定会被问到这个问题:Jev 这类模型和 ChatGPT 到底差在哪,为什么快那么多。最容易的错误答案是「Jev 是个更小的模型」。它确实更小,但那不是重点。重点是它们在**解决不同的问题**。

ChatGPT 建模的是「给定上文,下一个 token 是什么」,产出的是语言;Jev 建模的是「给定状态和几个类型化问题,每个问题的答案分布是什么」,产出的是带校准概率的决策。TypeSafe 把这个对立叫做 **System 2**(慢、审慎、生成式推理)对 **System 1**(快、反射式判断)——借的是卡尼曼那两个系统的名字。一个能写诗、能推理、能干任何用文字表达的事;另一个只能回答你**预先定义好答案空间**的问题,但答得又快又稳。

## 四条轴

**算法**。ChatGPT 用自回归解码:要输出 N 个 token,就要跑 N 次前向,每一次都以之前所有 token 为条件,并读一遍不断增长的 KV cache。Jev 用一次前向:把输入过一遍,在分类头上读出 logits——没有采样循环,没有随序列增长的缓存,答案不是「生成」出来的,是「读」出来的。

**架构**。ChatGPT 是解码器-only 的 Transformer,因果(单向)注意力,上千亿参数。Jev(以及独立复现它的 Laya、Von)是编码器式的双向 Transformer,几亿参数——双向没问题,因为你不是从左到右逐字往外吐。选项被编码成一段文本拼进输入(这就是为什么标签一多就抢 token 预算,见 LY2)。

**训练目标**。这是最根本的分界。ChatGPT 优化的是下一个 token 的似然,再加 RLHF。Jev 优化的是一个**严格适当评分规则**——直接把校准的概率作为目标(TypeSafe 称之为 RLCD,但从未公开到可复现;开源平替用交叉熵加 Brier 加温度缩放来逼近)。前者的副产品是流畅的文字,后者的副产品是可以直接卡阈值的概率。

**服务栈**。ChatGPT 那一侧是 vLLM / TensorRT-LLM,加上分页 KV cache、连续批处理、投机解码、跨卡张量并行——一整套为「让自回归可忍受」而生的工程。Jev 那一侧没有自回归要优化,栈直接塌成一个 FastAPI 进程、显存常数、CPU 也能跑,批处理就是把几个问题塞进一次前向。

## 为什么快:三个相乘的效应

1. **一次前向对 N 次前向**。这是最大的一项。把一个决策写成 JSON 可能要生成三十到一百个 token,而每个 token 是一次**独立**的全网络前向。编码器把输入过一次就读出答案,答案没有长度,没有可迭代的东西。
2. **模型小一百到一千倍**。四亿参数对上千亿,每一次前向本身也便宜得多。
3. **没有自回归机械**。没有采样循环,没有随序列增长的 KV cache,没有为追回速度而搭的投机解码脚手架。显存常数,连并发规划都变成算术(见 OP2)。

三者相乘,就是 TypeSafe 那个「快 193 倍、便宜 445 倍」的招牌,以及 Laya 更保守的实测约 7 倍。决策台上把「LLM 要吐多少 token」和「LLM 规模」拖起来,你会看到总加速是这两项相乘出来的。

## 诚实边界

两件事必须说清。第一,Jev 的内部**从未公开到可复现**,上面这张表里的架构是开源平替独立**再推导**出来的,不是从 Jev 拆出来的——所以别把它当成 Jev 的确证。第二,这**不是一个更好的 ChatGPT**。它不能写、不能总结、不能开放式推理。你用它,是把它当成一个快速、校准的**决策头**,放在 LLM 旁边或前面(比如前置一道注入检测、或者做小模型/大模型的路由),而不是拿它替代 LLM。选错了用途,再快也没用。

**练习**:把你手上一个「让 LLM 输出 JSON 再解析」的地方,数一数它每次要生成多少 token。用决策台把这个数填进「LLM 要吐多少 token」,看看理论上换成一次前向能省多少——再回到 VI 模块,用你自己的数据验证它在准确率上付不付得起这个代价。
