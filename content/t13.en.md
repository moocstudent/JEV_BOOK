## The encoder camp: small, fast, breaks as labels grow

The encoder camp makes one choice in common: take a BERT-family bidirectional encoder, fine-tune it on decision tasks, keep parameters between 150M and 420M, and buy tens-to-hundreds of milliseconds with CPU deployment.

@fig t13-encoder

- **Von** (ModernBERT-Large 395M, Apache-2.0): self-reported ~18 ms, 72.0% on the v2 suite against Jev's 96.6%, ships a `/v1/systemone`-compatible server, so `pip install von-sdk` then `von serve` stands in for Jev.
- **Verdict / NanoJev-151M** (151M, Apache-2.0): self-reported 77.10% accuracy, Brier 0.0636, ECE 0.0144, supports abstention, runs in-browser on WebGPU — the only realistic option for edge and privacy-sensitive settings.
- **jeff** (GLiFormer 400M, MIT): classification only, no score or noul.
- **OpenDecision** (~400M, Apache-2.0): needs no GPU, and its README states plainly that confidence measures distribution concentration rather than calibrated probability — honesty worth recording.

## Latency is accuracy too

Von overtakes Jev in real-time ViZDoom, 9.00 kills to 5.62. That contrast is instructive: when decisions come fast enough that latency itself decides the outcome, a 72-point fast model beats a 96-point slow one. Accuracy is not the only axis — in a loop that judges ten times a second, a model that cannot answer in time is deciding on stale state, however accurate it is.

**Exercise**: estimate your decision frequency. In a many-per-second control loop, put latency ahead of accuracy; in asynchronous ticket routing, accuracy leads.
