## Can it do code review? Triage, not the review

The honest answer splits in two. A System One model — Jev or Laya — **cannot write a review**: it generates nothing, so it cannot explain a bug, point at a line, or propose a patch. What it **can** do is answer typed questions about a diff in one forward pass: can this hunk skip a human, what kind of risk is it, how bad would it be if it were wrong. That is exactly the job a reviewer does in the first ten seconds of looking at a change, and it is the job that eats most review time, because most hunks are fine.

So the right frame is not 'a model that reviews code' but **a model that decides which code needs reviewing**. It is the two-tier system of OP3 with a diff as the state.

## Which type in the ternary language?

The book's three primitives — choice / score / noul — are the whole 'ternary' vocabulary. Code review maps onto them like this:

| Question | Primitive | Why |
|---|---|---|
| Can this hunk skip review? | **choice, k=3**: `approve` / `request_changes` / `needs_human` | The core question. It looks binary but has a third outcome — 'I can't tell from this hunk' — and SO2's rule is that yes/no/unsure is a choice, not a noul. |
| What kind of risk? | **choice, k=4**: `none` / `security` / `correctness` / `performance` | Decides who the escalation goes to. Keep k small: each label competes for `head_max_len` (LY2). |
| How bad if wrong? | **score**, 4 levels: cosmetic → outage | An ordered scale. Read the distribution, not only the expectation: a bimodal 'cosmetic or outage' averages to a harmless-looking 1.5 (SO2). |
| Does it touch auth / has tests / changes a migration? | **none — compute it** | These are facts in the file paths and the diff. A regex is free, exact and needs no calibration (OS3). |

The one-line answer: **code review is a `choice` problem**, with `score` for severity as a second question in the same call. Avoid `noul` twice over: the verdict has three outcomes, and even for genuinely binary questions Laya's noul follows its `false:`/`true:` labels (#156, LY3) — use a two-option choice with neutral keys instead.

**Decide the gate asymmetrically.** Only a confident `approve` skips a human. A confident `request_changes` still goes somewhere that can *write* — an LLM reviewer (System 2) drafts the comment, because a block without a reason is useless to the author. `needs_human`, or any confidence below θ, goes to a person.

## What Laya adds that matters for review

'Improve Jev with Laya's functions' is concrete here. Jev's public surface is one hosted endpoint (JV1). Laya ships the same protocol plus four things a review gate needs:

| Capability | Jev | Laya | Why it matters for code review |
|---|---|---|---|
| Runs on your machine | no — hosted API | yes — local CPU (LY4) | **Source code never leaves your network.** For most teams this alone decides it. |
| Same `/v1/systemone` protocol | the reference | `laya-serve` (OP1) | The review service targets one schema; switching backend is one URL. |
| Fine-tune on your data | no public path | `proper_reward` + `detach_encoder` (LY4 appendix) | **Your merge history is free labels**: merged untouched → approve, 'changes requested' → request_changes, reverted → a missed defect. |
| Checkpoint routing | — | `Router` (LY1) | Code is mostly English identifiers: route to the English checkpoint, which also avoids the multilingual score position bias (#131). |

The fine-tuning row is the important one. CS1's failure lesson was 'don't swap models, fine-tune the base on your own rows'. Code review is the rare task where those rows already exist, labelled, in your git host.

## The token budget decides the unit: the hunk

The English checkpoint's `max_len` is 512 with 192 reserved for options, leaving roughly **300 tokens** for the diff (LY2). A whole push does not fit; a hunk usually does. So the unit of decision is the hunk, and a hunk over budget is cut into windows — never silently truncated, because the bug may be in the part the model did not see.

That choice has a consequence the bench makes visible: **a push is only as clear as its worst hunk.** If a fraction c of hunks auto-pass, a push of n hunks auto-passes only with probability cⁿ — at c=0.7 and n=10 that is 2.8%. Per-push automation collapses. The value is somewhere else: the reviewer is handed only the hunks that did not pass, so review load drops by c even when almost no push is fully automatic.

## Wiring it into TaskaaS over MCP

This book does not document TaskaaS's own API. The integration assumes only two things of it: it can be **triggered by a push** (webhook or git hook), and it can act as an **MCP client** — call a tool on an MCP server. If it can do both, nothing inside it needs to change.

The server, `typed-review`, exposes one MCP tool, `review_push(diff, repo, ref)`:

1. Split the diff into hunks (windows if over budget).
2. For each hunk, POST one `/v1/systemone` request with the three questions above — to Jev, or to a `laya-serve` on your network.
3. Gate each hunk: `auto_pass` / `llm_review` / `human_review`.
4. Return the push action (the worst hunk's) and **only the hunks that need eyes**.

TaskaaS then turns that result into work: a pass status, an LLM-review task carrying the flagged hunks, or a human-review task assigned by `risk`. The same script also runs without an MCP host (`--check`) for a local pre-push hook or CI.

Two production rules carried over from OP3:

- **Degradation path.** When the model is unreachable, every hunk becomes `human_review`. That is a choice — fail closed — and it must be agreed with the team before the incident, not during it.
- **Monitoring.** Watch the **override rate**: auto-passed hunks later reverted, or flagged hunks a reviewer approved untouched. It is the only labelled online signal, and it is also the next fine-tuning set.

## Honest boundary

This book has **not measured** code review with Jev or Laya; the bench runs on a synthetic set, and the threshold, coverage and escape rate you will get are unknown until you measure them. Measure the way EV1–EV3 teach: build the eval set from a few hundred past hunks with the labels your git host already holds, run the three baselines (the keyword baseline here is a linter plus path rules), then read the threshold curve. A gate that auto-passes 40% of hunks at an acceptable escape rate is a real win. A gate that only passes whitespace changes is a linter with extra steps.

**Exercise**: export your last 300 merged hunks with their review outcome. Label them approve / request_changes / needs_human from that history alone, and count how many are `approve` — that share is the ceiling on the review load this gate can ever save.
