## You may not need a System One model at all

This chapter is where the module lands and is the book's cheapest lesson. There are four routes to a typed decision, and a System One model is only one of them.

@fig t15-routes

1. **Fine-tune a classifier**. With fixed labels and a few hundred annotations, a fine-tuned ModernBERT or SetFit gives latency in the same class, and calibration you measured yourself without trusting anyone's README — the price is a training pipeline and a labelled set.
2. **Constrained decoding**. Outlines and XGrammar restrict decoding to a grammar or schema and guarantee structurally valid output. But be clear: they solve **format**, not probability — what you get is still a string with no calibrated probability. That is the dividing line from a System One model, and where selection debates conflate the two.
3. **Read the logits**. If you already run an LLM, read the log-probabilities of the option tokens, adding no component — precisely SemIf's approach.
4. **A System One model itself**. Its unique value is one thing: an out-of-the-box, cross-task decision interface carrying calibrated probabilities.

## The conclusion is blunt

With one task and labelled data in hand, the first route almost always wins; System One models win on many tasks sharing one interface, not on any single task's metrics.

**Exercise**: place your setting against the four routes on six dimensions — latency, calibrated probability, need for labelled data, components added, cross-task reuse, maintenance surface. You will see more clearly which one you should take.
