## What you want is not prose, it is a value you can branch on

Your code needs a judgement: which department owns this ticket, is this comment abusive, should this request go to the small model or the large one. For three years the standard move was to write a prompt, have the LLM emit JSON, and parse the field out. It runs, but its failure modes are peculiar — invalid JSON, valid JSON whose field names drifted, two answers to one input, an enum with one letter wrong.

@fig t1-pipes

So a layer of patches grew: constrained decoding for the grammar, schema validation against dirty data, retries and repair prompts for the rest. Those fix the **format** and leave the deeper problem untouched — there is no probability behind the string you got back. You do not know how sure the model was, so you can only trust it wholesale or not at all.

## Four failures and their costs

- **Truncation / invalid JSON**: a hard failure that errors, retries can recover, but retries push P99 to several times P50.
- **Field drift / misspelled enum**: the dangerous class. The JSON is valid, validation passes, the value is wrong — nothing errored, and retries cannot help.

The System One proposal skips this layer: feed in program state and some typed questions, get answers with probabilities, no text generated and nothing to parse.

## When the detour is not worth replacing

If you already run an LLM and the judgement is rare, the extra cost of generate-then-parse is negligible. The payoff arrives on **high-frequency small decisions** — millions a day, each needing one enum and one probability.

**Exercise**: find one place in your code that has an LLM emit JSON and parses it, and count the lines handling format failure. Those lines are what you pay for a capability you did not need.
