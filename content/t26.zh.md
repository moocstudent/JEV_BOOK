## 三个位置,别混为一谈

「模型在本地、在一个外部库里、还是在远端?」这个问题之所以让人困惑,是因为「模型」这个词藏了三个住在不同地方的东西。

@fig t26-runtime

- **① 你的脚本**(比如本书配套 demo 的 `laya_check.py`)在**本地**,而且**不含任何模型和权重**。它只是编排加纯 Python 的统计:ECE、温度网格搜索、门槛表。它跟模型的全部接触只有两行——`laya.load(...)` 和 `agent.predict(...)`。
- **② `laya` 这个 pip 库**也在**本地**,但它**也不含权重**。它只有九个很小的 `.py` 文件(约 117 KB),是加载和运行模型的**代码**;真正的张量计算交给它依赖的 `torch` 和 `transformers`。
- **③ 权重**才是那个约四亿参数的神经网络。它从 Hugging Face(`convaiinnovations/laya`)**远端下载、本地缓存**到 `~/.cache/huggingface`(english 843MB / multilingual 678MB / typed-decisions 846MB)。

**关键结论**:一旦权重缓存好,推理**百分之百在你本地的 CPU 上跑**,调用 `agent.predict` 不会向任何远端 API 发一个字节。这正是它和 Jev 的根本区别——Jev 是一个你 POST 过去的托管远端 API,Laya 是你自己在本地跑的开源实现。唯一的远端步骤是那一次性的权重下载。

## 加载:一次前向之前发生了什么

`laya.load()` 走的是 `Agent.__init__`:如果本地没有这个 checkpoint,就 `snapshot_download` 从 HF 拉下来(用 `allow_patterns` 只拉这一个 checkpoint 需要的 `model.safetensors`、`rl_agent_config.json`、`tokenizer/`、`encoder/`),然后 `build_model()` 按配置重建网络、`load_state_dict(weights, strict=True)` 把训练好的参数灌进去。设备在这里自动落到 CPU(没有 CUDA)。出厂温度也在这一步被读进来并 **clamp**——那个 0.1006 的 `choice:11+` 桶就是在这里被 `TEMP_MIN=0.5` 拒绝的。

## 那个外部库的模型:DecisionModel

库里的模型是 `DecisionModel`(`common.py`),结构是:

```
DecisionModel =
    encoder      # 双向编码器:ModernBERT-large(英)/ mmBERT-base(多语言)
  + type_emb     # nn.Embedding(3, d):每种问题类型一个学到的向量
  + head         # 一个两层的小 nn.TransformerEncoder
  + scorer       # LayerNorm → Linear(d,d) → GELU → Linear(d,1):把任意 token 打成一个标量
```

**最关键的设计:没有固定的分类头。** 常规分类模型是分类头上一个类别一个神经元;Laya 不是。它的 `scorer` 把*任意一个* token 的隐向量映射成一个标量——所以选项可以是任意文本,也因此选项要和正文抢 token 预算(见 LY2)。

## 一次前向的六步

`agent.predict` = `agent.system_one`,在**一次非自回归的前向**里做完(`common.py` 的 `DecisionModel.forward`):

1. **选项变成带标记的文本**。`build_sequence()` 把 state + instructions + 每个选项拼成一条 token 序列,并在每个选项处记下一个「标记」的位置。
2. **一次编码器前向**。`h = encoder(input_ids, attention_mask).last_hidden_state`——双向的,每个 token 看得见其它所有 token(没问题,因为不逐字生成)。
3. **注入问题类型**。`h = h + type_emb(qtype)`。
4. **小 head 精修** `h`。
5. **在标记处 gather**。`m = gather(h, marker_pos)` 把每个选项标记处的隐向量取出来,`logits = scorer(m)` 打成**每选项一个 logit**;padding 标记被 mask 成 `-1e4`。
6. **变成类型化答案**(`agent.py`):`z = logits[:k] / t_scale`,`p = softmax(z)`。choice 取 argmax;score 取有序期望 `Σ i·p[i]`;noul 取 `p[1]`。`confidence = 1 - H(p)/log(k)`——归一化熵,**不是概率**(见 CA1)。

这个「给每个选项标记打分再 softmax」的机制,一句话解释了它为什么快(一次前向、无生成循环、无 KV cache),也解释了它为什么标签一多就垮(77 个标记都在同一条序列里抢 `head_max_len` 的位置)。

## 诚实接缝:能复现推理,不能复现训练

上面这套推理代码里**没有** RLCD——那个让概率变得校准的训练方法。它只烘焙在 `model.safetensors` 里。运行时只是**应用**训练的产物(读 `rl_agent_config.json` 里的分桶温度、并拒绝烂掉的那个)。所以这个开源库能一字不差地复现 Laya 的**推理**,但让它校准的**训练**只被近似——这就是为什么每个「开源 Jev」都是再推导,不是复刻。

**练习**:在你自己机器上跑 `pip show -f laya` 看库有多小、里面有没有 `.safetensors`;再 `du -sh ~/.cache/huggingface/...` 看权重在哪、多大。亲眼确认「库」和「权重」是两个东西。

## 附录 · 运行时、切换与再训练

上面讲了「怎么跑」,这个附录回答三个紧接着的问题:权重在磁盘上长什么样、能不能换模型、能不能再训练。

### HF 缓存到底是什么

`~/.cache/huggingface/hub/models--convaiinnovations--laya/` 不是一堆模型文件,而是一个**内容寻址的 git 镜像**:

@fig t26-cache

- `refs/main` —— 40 字节,记着 `main` 指向的 commit SHA。
- `blobs/` —— 真正的文件内容,每个按哈希命名、跨版本**去重**(本机 10 个 blob,1.5GB)。
- `snapshots/<SHA>/` —— 某个 git 版本的视图,里面每个文件都是**指向 blobs 的软链接**,不是真副本。这就是为什么下两个版本、下崩了续传都不会重复占空间。

一个 snapshot 里**打包了两个 checkpoint**:根目录是英文(ModernBERT-large,`model.safetensors` 843MB),`multilingual/` 子目录是多语言(mmBERT-base,644MB)。注意 `typed-decisions/` **不在**——`allow_patterns`(`agent.py`)只拉你 `load` 过的那个 checkpoint,我只用了英文和多语言,第三个就没下。每个 checkpoint = `model.safetensors` + `rl_agent_config.json` + `tokenizer/` + `encoder/config.json`。

### 能不能换模型?怎么换?

能,三个层次,但有一条硬边界。

- **在打包的几个 checkpoint 之间**:`laya.load("convaiinnovations/laya", subfolder="multilingual")`(或 `"typed-decisions"`),或者交给 `Router` 按语言自动选(LY1)。
- **换成任意仓库或本地目录**:`laya.load("some-org/my-ckpt")` 或 `laya.load("./my_run")`。
- **换不了的**:一个裸的 base BERT。加载器 `_verify_compatibility`(`agent.py`)要求这是一个 **Laya 格式的决策 checkpoint**——config 里得有 `encoder` 和 `head_layers`,safetensors 里得有 `encoder.` + `type_emb.` + `scorer.` + `act_head.` 这几组前缀,而且 `strict=True` 逐个查形状。一个普通 ModernBERT 没有决策头,直接被拒。你也不能脱离决策头单独换编码器——它俩是一起训出来的一个整体,config 里的 `encoder` 字段只是告诉库「先按这个架构搭一个空壳,再把训练好的权重灌进去」。

### 一个模型要满足什么才加载得了

| 文件 | 必需 | 作用 |
|---|---|---|
| `rl_agent_config.json` | **是** | 至少要有 `encoder`(一个 transformers id/目录)和 `head_layers`;还有 `max_len` / `head_max_len` / `temperature` / `temperature_by_options` |
| `model.safetensors` | **是** | state_dict 必须和 `DecisionModel(encoder, head_layers, n_act)` 严格对上 |
| `tokenizer/` | 建议 | 没有就退回用编码器自带的 tokenizer |
| `encoder/config.json` | 建议 | 让它离线重建架构,不用再去下 base 模型 |

运行时:Python 3.10–3.13(不是 3.14)、`torch≥2.0`、`transformers≥4.48`(要 ModernBERT 支持)、`safetensors`、`huggingface_hub`、`numpy`。

### 能不能再训练?——能,而且这才是正道

三条证据都在磁盘上:

- **base 本来就是拿来特化的**。README 写明 base checkpoint 在 typed-decisions 上零样本近乎随机(0.362 对随机 0.318),0.766 是在那份基准自己的训练集上微调出来的。英文 checkpoint 的 config 甚至记着 `"fine_tuned_from_checkpoint": true`、`"updates": 7313`、`"hours": 1.96`——它自己就是微调出来的。
- **库里带着训练目标**。`common.py` 有 `proper_reward`(对数 + 球面 + 排序概率的**严格适当评分规则**),和 `td_lambda_targets`、`ece_score`、`DecisionModel`、`build_model` 一起公开导出。完整训练循环在 README 指的那个微调 notebook 里(在留出集上拟合校准、清掉旧温度、推回 hub)。
- **它为便宜的微调留了口子**。`DecisionModel.forward` 有个 `detach_encoder` 参数——打开它就**冻住编码器只训练决策头**,这是本机这种没 GPU 的机器唯一现实的路子;全量微调那 400M 编码器要 GPU(notebook 面向 2×T4)。

**再训练的配方**:`build_model(cfg, encoder_dir)` 建模 → 前向出分布、对着你的标注目标算 `proper_reward` 反传(训头,可选训编码器)→ 在留出集上按(问题类型 × 选项数)分桶各拟合一个温度 → 把 `model.safetensors` + `rl_agent_config.json` 存到一个目录 → `laya.load("./那个目录")`。这正是本书失败案例(CS1/t22)给佳悦数据开的药方:别再换模型了,拿自己的数据把 typed-decisions checkpoint 微调一下——base 是底座,不是成品。

### 配套 demo:agent 与微调(实测)

这一章的道理都做成了可跑的东西,在配套仓库 `layademo`(Gitee):

- **`app.py` · FastAPI 决策 agent**(master 分支):把 Laya + 模块体系包成一个带**门槛分流**的服务——`/classify` 返回模块 + confidence + `action`(auto/escalate),`/triage` 一次前向同时给 模块+优先级+是否结构改动,`/batch` 给自动率汇总。就是 OP3 的两级架构。实测里它诚实地工作:一条被误分到「财务核算」的低置信度需求被门槛正确地 `escalate` 了;`/triage` 三问一次前向热态 ~900ms。每个响应都带 `note` 说明 confidence 是归一化熵不是概率、base 未微调是路由提示不是事实。
- **`train.py` · 冻结编码器微调**(train 分支):把 LY4 附录那套再训练配方跑通——冻住编码器、只用 `proper_reward` 训决策头、留出集拟合温度、存成 `laya.load` 能直接读回的 checkpoint。本机 CPU、合成样例、120 行 / 5 epoch 实测:**准确率 0.733 → 0.767**(loss 0.44→0.34 单调下降),重载自盘一致。涨幅只有 +3.4 点不是脚本的问题——剩下的错误是那两对故意留的语义重叠标签(库存管理/仓储作业、生产计划/生产执行),正是 CS1 那一课:任务问题,不是模型问题。要真顶上去得解开编码器全量微调(要 GPU)或先合并重叠标签。

一句话:**agent 证明了两级门槛在真实服务里成立,微调 demo 证明了「别换模型、微调 base」这条路能跑通并给出真实增量**——两者都不是纸上谈兵,数字都是本机实测的。
