## 它能做代码评审吗?能做分诊,不能写评审

诚实的回答分两半。System One 模型——不管是 Jev 还是 Laya——**写不了评审**:它什么都不生成,所以它没法解释一个 bug、指出是哪一行、或者给出补丁。它**能**做的,是在一次前向里回答关于一段 diff 的几个类型化问题:这一块能不能跳过人工、它是哪一类风险、如果错了有多严重。这恰好是一个评审者看一段改动的头十秒在做的事,也恰好是吃掉大部分评审时间的那件事——因为大多数改动块都没问题。

所以正确的定位不是「一个会评审代码的模型」,而是**一个决定哪些代码需要评审的模型**。它就是 OP3 的两级架构,只不过 state 换成了一段 diff。

## 在三元语言里它适合哪个类型?

本书的三个原语——choice / score / noul——就是全部的「三元」词汇。代码评审映射到它们上面是这样的:

| 问题 | 原语 | 为什么 |
|---|---|---|
| 这一块能跳过评审吗? | **choice,k=3**:`approve` / `request_changes` / `needs_human` | 核心问题。它看起来是二元的,其实有第三种结局——「光看这一块判断不了」——而 SO2 的规矩是:是/否/不确定是 choice,不是 noul。 |
| 哪一类风险? | **choice,k=4**:`none` / `security` / `correctness` / `performance` | 决定升级给谁。k 要小:每个标签都在抢 `head_max_len`(LY2)。 |
| 错了有多严重? | **score**,4 级:外观 → 事故 | 有序量表。要看分布而不只看期望:一个「要么外观要么事故」的双峰分布,平均出来是个看似无害的 1.5(SO2)。 |
| 是否碰了鉴权 / 有没有测试 / 是否改了迁移? | **不问模型——直接算** | 这些是写在文件路径和 diff 里的事实。一条正则免费、精确、不需要校准(OS3)。 |

一句话答案:**代码评审是一个 `choice` 问题**,同一次调用里再加一个 `score` 问严重度。`noul` 要避开两次:判决本身有三种结局;而即使是真正二元的问题,Laya 的 noul 也会跟着它的 `false:`/`true:` 标签走(#156,LY3)——改用中性键的两选项 choice。

**门槛要不对称地定。**只有高置信度的 `approve` 才能跳过人工。高置信度的 `request_changes` 仍然要送到一个会**写**的地方——由一个 LLM 评审者(System 2)起草评论,因为一个不给理由的拦截对作者毫无用处。`needs_human`,或者任何置信度低于 θ 的,交给人。

## Laya 多出来的、对评审有用的能力

「用 Laya 的功能增强 Jev」在这里是具体的。Jev 的公开接口只有一个托管端点(JV1)。Laya 提供同一个协议,外加评审闸门需要的四样东西:

| 能力 | Jev | Laya | 对代码评审为什么重要 |
|---|---|---|---|
| 在你自己的机器上跑 | 否——托管 API | 是——本地 CPU(LY4) | **源代码不出你的网络。**对大多数团队,光这一条就决定了选择。 |
| 同一个 `/v1/systemone` 协议 | 参照实现 | `laya-serve`(OP1) | 评审服务只对一个 schema 编程,切换后端只改一个 URL。 |
| 用你的数据微调 | 没有公开途径 | `proper_reward` + `detach_encoder`(LY4 附录) | **你的合并历史就是免费标签**:原样合并 → approve,被要求修改 → request_changes,事后被回滚 → 一个漏掉的缺陷。 |
| checkpoint 路由 | — | `Router`(LY1) | 代码主要是英文标识符:路由到英文 checkpoint,顺带避开多语言版 score 的位置偏置(#131)。 |

最重要的是微调那一行。CS1 失败案例的教训是「别换模型,在你自己的数据上微调底座」。代码评审是少有的那种任务:这些数据已经存在,而且已经在你的 git 平台上打好了标签。

## token 预算决定了单位:改动块(hunk)

英文 checkpoint 的 `max_len` 是 512,其中 192 留给选项,留给 diff 的大约只有 **300 个 token**(LY2)。一整次推送放不进去,一个 hunk 通常放得下。所以决策的单位是 hunk;超预算的 hunk 切成多个窗口——绝不静默截断,因为 bug 可能恰好在模型没看到的那一截。

这个选择有一个后果,决策台会让你看见:**一次推送的清白程度取决于它最差的那一块。**如果 hunk 的自动放行率是 c,一次 n 块的推送整体自动放行的概率只有 cⁿ——c=0.7、n=10 时是 2.8%。按推送算的自动化会崩塌。价值在别处:评审者只拿到没放行的那些块,所以即使几乎没有一次推送是全自动的,评审工作量也减少了 c。

## 通过 MCP 接进 TaskaaS

本书不描述 TaskaaS 自己的 API。这个集成只假设它能做两件事:能被**一次推送触发**(webhook 或 git hook),以及能作为 **MCP 客户端**——调用一个 MCP 服务器上的工具。只要两件都能做,它内部什么都不用改。

服务器 `typed-review` 暴露一个 MCP 工具,`review_push(diff, repo, ref)`:

1. 把 diff 切成 hunk(超预算的切窗口)。
2. 对每个 hunk 发一次 `/v1/systemone` 请求,带上面三个问题——发给 Jev,或者发给你内网里的 `laya-serve`。
3. 逐块过闸:`auto_pass` / `llm_review` / `human_review`。
4. 返回推送的动作(取最差那一块的),以及**只需要人看的那些块**。

TaskaaS 再把这个结果变成工作:一个通过状态、一个带着被标记 hunk 的 LLM 评审任务、或者一个按 `risk` 分派的人工评审任务。同一个脚本不需要 MCP 宿主也能跑(`--check`),用于本地 pre-push hook 或 CI。

从 OP3 带过来两条上线规矩:

- **降级路径。**模型不可达时,每一块都变成 `human_review`。这是一个选择——失败即关闭——必须在故障前和团队约定,而不是在故障现场临时决定。
- **监控。**盯**推翻率**:被自动放行、事后被回滚的块,或者被标记、评审者原样批准的块。它是唯一带标签的线上信号,也是下一轮微调的数据集。

## 诚实边界

本书**没有实测过** Jev 或 Laya 做代码评审;决策台跑的是合成数据,你实际能得到的门槛、覆盖率和漏检率,在你测之前都是未知数。按 EV1–EV3 的方法测:从过去几百个 hunk 建评测集,标签用你 git 平台上已经有的;跑三条基线(这里的关键词基线就是 linter 加路径规则);然后读门槛曲线。一个在可接受漏检率下自动放行 40% hunk 的闸门是真收益。一个只放行空白改动的闸门,就是一个多绕了几步的 linter。

**练习**:导出你最近合并的 300 个 hunk 和它们的评审结果。只根据这段历史把它们标成 approve / request_changes / needs_human,数一数有多少是 `approve`——这个比例就是这个闸门最多能帮你省下的评审工作量的上限。
